ASTRID HOSTED VOLUME FORMAT 1
=============================

Status: hosted-media recovery specification
Encoding: unsigned little-endian integers and canonical UTF-8 region names
Document line endings: LF

This is the hosted adapter for the path-free AstridVolume contract. The
principal store addresses named byte regions; it does not address host files or
directories. A bare-metal provider may use a different physical layout while
implementing the same region, transaction, and durability contract.

The hosted container starts with these exact eight bytes:

  41 53 54 56 4f 4c 31 00        ASCII "ASTVOL1" followed by NUL

Every following record is:

  offset  size  field
  0     8  magic = 41 53 54 52 45 47 31 00 ("ASTREG1" + NUL)
       8     8  total_record_length, including this header, name, and payload
      16     8  sequence, starting at 1 and increasing exactly by 1
      24     1  operation
      25     2  region_name_length
      27     8  logical_offset
      35     8  payload_length
      43    32  checksum
      75     N  canonical UTF-8 region name
    75+N     M  payload

Generation-root images add a fixed dual-copy pointer immediately after the
container magic and before the first record:

  offset size field
  0    8  copy 0 magic = 41 53 54 52 4f 4f 54 31 ("ASTROOT1", without NUL)
  8    8  generation, unsigned little-endian and greater than zero
 16    8  canonical image base, unsigned little-endian
 24    8  offset of the selected EOF footer, unsigned little-endian
 32   32  pointer checksum
 64   64  copy 1, encoded exactly like copy 0

Copy 0 starts at byte 8 and copy 1 starts at byte 72; the fixed root occupies
bytes 8 through 135. The checksum is the 32-byte output of a BLAKE3
derive-key hasher using context "astrid volume root v1" over this exact
concatenation:

  root_magic[8]
  generation[8]
  root_base[8]
  footer_offset[8]

Recovery decodes each independently checksummed copy and selects the higher
valid generation. A torn or invalid copy is ignored. If either fixed slot
contains the root magic but neither copy is valid, recovery fails closed. A
file with no valid pointer and no root magic uses the generation-0 record and
EOF-footer rules below. When a valid root is present, its named EOF footer is
the only durability boundary; recovery must not substitute an EOF footer or
header scan from a different generation.

Same-inode publication constructs a complete replacement image and makes it
durable before a root flip. A second relocation flip makes byte 136 the
canonical image base. Physical truncation of the superseded image happens
only after both root copies select the relocated generation and the container
has been synced. Storage-capacity credit follows that truncation.

Region names are relative, slash-separated UTF-8. They are non-empty, at most
512 bytes, and reject empty components, dot components, dot-dot components,
backslashes, control characters, leading slashes, and trailing slashes.

The checksum is the 32-byte output of a BLAKE3 derive-key hasher using context
"astrid volume record v1" over this exact concatenation:

  sequence[8]
  operation[1]
  region_name_length[2]
  logical_offset[8]
  payload_length[8]
  region_name[N]
  payload[M]

Operation codes are:

  1  create an absent empty region; payload is empty
  2  overlay payload at logical_offset in an existing region
  3  set an existing region length to logical_offset; payload is empty
  4  remove an existing region; payload is empty
  5  rename an existing source to an absent destination named by payload
  6  replace an existing destination named by payload with an existing source
  7  commit a metadata transaction; region is exactly
      system/volume-metadata-transaction and logical_offset is zero
   8  durable commit boundary; region is exactly system/volume-commit,
      logical_offset is zero, and payload is empty

A mutation record is recoverable data but is not a durability boundary by
itself. Version one admits records only after the most recent operation-8
boundary. A physically short final record after the last boundary is an
uncommitted tail. Complete records without a later boundary are also an
uncommitted tail, including a terminal checksum-damaged record. A damaged
record with a later physically valid successor is interior corruption and
recovery fails rather than truncating it.

A metadata-transaction payload begins with u16 mutation_count, followed by
mutation_count entries. Each entry is u8 kind (1 rename, 2 replace), then a
u16 source length and source bytes, then a u16 destination length and
destination bytes. Count is 1 through 1024. All mutations validate and become
visible as one record or none become visible.

Recovery scans a contiguous sequence of records whose namespace transitions are
valid, then exposes the state at the latest operation-8 boundary. A physically
incomplete final record is truncated to that boundary. A damaged length cannot
hide a later physically valid record; that is interior corruption and fails
recovery. Write payload checksums are streamed with bounded memory. Non-write
payloads are bounded to 2 MiB before allocation.

sync() appends operation 8 when mutations are pending and returns only after
that boundary is durable. Graceful close performs the same boundary. A crash
before the boundary can discard the uncommitted tail. HostedFileVolume holds an
exclusive lock for the open lifetime. The engine close boundary releases that
lock even when other references to the closed engine remain.
